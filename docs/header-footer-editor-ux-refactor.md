# Header and Footer Editor UX Refactor

Last modified: 2026-06-01

## Objective

Upgrade the Header and Footer manager editors into focused, visual editors that feel closer to the Page editor while preserving Aero CMS vertical-slice boundaries.

The editors should support:

- Live preview while editing.
- A constrained block palette appropriate for site chrome.
- Culture / translation management like Page and Post editors.
- AI translation actions using the existing AI provider infrastructure.
- Public rendering through existing Tailwind/HTML renderers, not NeoUI components.

## Architecture Decision

Do not introduce a shared persisted header/footer block model.

Navigation and Footer remain separate vertical slices:

- `Aero.Cms.Modules.Navigation` owns header/navigation domain models, persistence, API, rendering, and translation workflows.
- `Aero.Cms.Modules.Footer` owns footer domain models, persistence, API, rendering, and translation workflows.
- `Aero.Cms.Shared` may provide editor UI components and conventions, but it should not own module persistence shapes.
- NeoUI may be used for manager editor primitives, drag/drop affordances, panels, and palettes.
- Public CSHTML/runtime output must remain plain HTML/Tailwind generated by each module renderer.

This keeps SRP intact and avoids creating a generic site-chrome abstraction before the separate domains prove they need one.

## Header Editor Scope

The header editor continues to evolve the existing Navigation implementation.

Current domain anchor:

- `NavMenuSnapshot`
- `INavMenuComponent`
- `NavLink`
- `NavMenu`
- `NavHtml`
- `NavSearch`

Header-only settings:

- Sticky header.
- Transparent-on-scroll.

Shared-style settings owned by Navigation for header usage:

- Hide globally.
- Background image.
- Gradient.
- Background color.
- Padding / margin.
- Alignment.
- Visibility trigger.

Header block palette:

- Column / container.
- Image or logo.
- Icon only.
- Text with optional icon.
- Menu list with optional icon.
- Rich menu / mega menu.
- Button.
- Social media button.
- Social media button group.
- Search box.
- Custom HTML.

The palette may expose these as editor blocks, but the saved shape should map into Navigation-owned records.

## Visibility Triggers

Support the common header/footer visibility behaviors through module-owned settings:

```csharp
public enum ChromeVisibilityTriggerMode
{
    None,
    ScrollThreshold,
    ElementId,
    ViewportSentinel
}
```

Recommended fields per module:

```csharp
public ChromeVisibilityTriggerMode VisibilityTriggerMode { get; init; }
public int? ScrollThresholdPx { get; init; }
public string? TriggerElementId { get; init; }
```

Initial behavior:

- `None`: always visible unless hidden globally.
- `ScrollThreshold`: activate/hide/change style after a configured scroll offset.
- `ElementId`: activate/hide/change style when the target element exists and reaches the configured point.
- `ViewportSentinel`: use an `IntersectionObserver` sentinel to toggle visibility/style when a section enters or exits the viewport.

The public renderer should emit stable data attributes and Tailwind classes. A small shared runtime script can implement the behavior, but the setting remains owned by the module document.

## AI Translation UX

Page and Post editor translation tabs should gain:

- `Translate all` button.
- `Translate` button per missing culture entry.
- Optional overwrite checkbox for existing variants.

Default behavior:

- Translate only missing supported cultures.
- Preserve existing variants unless overwrite is explicitly checked.
- Send one AI request per target culture.
- Use `Task.WhenAll()` to await all target-culture translation tasks.
- Each culture translation task returns its own `Result<T>` so one failed culture does not cancel successful cultures.
- Report per-culture success/failure in the UI.

Header and Footer editors should follow the same pattern after their editor shells expose culture tabs.

## AI Translation Payload Rule

Do not send raw persisted documents or block graphs to the LLM.

Use the field-key payload shape from `docs/ai-translation-implementation.md`:

- Stable field keys.
- `ContentFieldHint`.
- Source culture.
- Target culture.
- Optional provider ID.

Each module owns extraction and rehydration:

- Pages translate whitelisted user-facing page/block fields.
- Posts translate title, excerpt, SEO fields, and markdown content.
- Navigation translates header/menu labels, alt text, rich-menu text, button labels, and custom HTML text nodes where safe.
- Footer translates company/tagline/legal text, group titles, link labels, button labels, search placeholder, and custom HTML text nodes where safe.

## Custom HTML Safety

Custom HTML is allowed for non-admin users, but it must be sanitized.

Minimum rules:

- Remove scripts.
- Remove inline event handlers.
- Reject dangerous URL schemes such as `javascript:`.
- Allow a constrained list of safe tags and attributes.
- Preserve safe Tailwind classes where possible.
- Render sanitized HTML intentionally; never treat arbitrary custom HTML as safe by default.

## Implementation Order

1. Add Page/Post AI translation actions:
   - single-culture translate
   - translate all missing cultures
   - overwrite option
   - per-culture result reporting
2. Add Navigation/Header AI translation endpoint and client method.
3. Add Footer AI translation endpoint and client method.
4. Refactor Header editor into a visual editor shell:
   - palette
   - live preview
   - property panel
   - culture / translation tab
5. Refactor Footer editor into the same visual pattern with Footer-owned blocks.
6. Add visibility trigger settings and public runtime behavior.
7. Add custom HTML sanitizer before exposing custom HTML broadly.

## Out of Scope

- Shared persisted header/footer block model.
- Generic site-chrome module.
- PageEditor-style full marketing/page blocks in Header/Footer.
- Automatic publish after AI translation.
- Bulk/background translation jobs.
